## 1. v1.0 的定义：什么叫"功能完备"

MVP 证明了一件事：一句话任务可以被受控地执行和交付。但它还不是一个每天打开的工作伙伴。差距不在功能数量，而在三个使用姿态上：

1. **MVP 是"发起一个任务看着它跑完"，v1.0 要做到"同时挂着五个任务去干别的"**——这需要真正的任务中心、队列调度、定时任务和可靠的通知回路；
2. **MVP 的任务是一次性的，v1.0 的任务是可对话推进的**——交付后说一句"第三节展开写"，系统增量重跑而不是新开任务；
3. **MVP 只有一个模型一条通道，v1.0 要按步骤选择合适的模型和工具**——规划用强模型、抽取用快模型、本地能干的不出网。

由此给 v1.0 一个可验收的定义：

> **用户可以把一周的高频工作（研究、内容、文件处理）全部交给 LeanClaw：多任务并行受控、交付后可对话式修改、成本可预算、模型可切换、经验可沉淀复用；应用可打包分发、可自动更新。**

明确不属于 v1.0 的（继续冻结）：多人协作、企业权限、插件市场、跨设备同步、完整 Computer Use、综合 TPS 评分。

## 2. 现状盘点：MVP 有什么、缺什么

### 已具备（经审计验证）

执行引擎全链路（状态机 / 账本 / 检查点 / 幂等 / 崩溃恢复）；三条 Recipe；三级验证 + Evidence 逐字核验；Andon / Approval / 三级风险；五视图 UI + 动效规范；任务预设；safeStorage 密钥；Run Inspector 与复盘卡；Electron 43 + audit 归零；9 场景冒烟回归基线 + 63 单测。

### 明确缺口（按用户痛感排序）

| # | 缺口 | 现状 | 痛感 |

## 3. 功能规划

按六个主题域展开。每项标注优先级（P0 = v1.0 必须；P1 = v1.0 应有；P2 = v1.0 之后）、对应缺口、验收标准。

### 3.1 任务系统：从"单任务陪跑"到"多任务托管"

**F1 对话式增量 Run（P0，G1）**——v1.0 单个最重要的功能。任务页底部输入框激活：任务处于 Delivered/Blocked/停驻状态时，用户输入修改指令 → Runtime 创建增量 Run（复用原任务上下文与 Artifact，模型判断受影响步骤范围，从最近可用检查点起跑）→ 新版本 Artifact 自动取代旧版（版本链已具备）。运行中输入则作为补充信息注入下一步。
验收：对已交付研究报告说"第二节展开对比"，系统只重跑生成+验证+写入，Deliverable 出现 v2，v1 可回看；全过程不新建 Task。

**F2 Tasks 独立页（P0，G2/G11）**——一级导航加 Tasks：默认列表视图，筛选器 All / Running / Need You / Delivered / Blocked / Scheduled / Archived；行内快捷操作（暂停/恢复/归档）；批量归档。轻量看板作为第二视图（按用户可见状态分列）。
**一条硬性产品规则：看板卡片不允许拖拽改状态。** 状态由 Runtime 和验证门决定，不由手势决定——这是 TPS 控制层在 UI 上的延伸。拖拽只允许调整同列内的用户优先级（影响队列出队顺序）。
验收：20 个任务时 Home 只显示需要处理的和进行中的，其余在 Tasks 页可筛可归档。

**F3 WIP 调度器（P0，G3）**——Runtime 增加队列：同时活跃 Run 上限（默认 3，设置页可调）、高成本模型并发上限（默认 1）、fs.write/Shell 类工具全局串行。超限任务停在 queued 并显示"排队中（第 N 位）"。
验收：同时发起 5 个任务，只有 3 个进入执行，其余排队；全部正常交付；账本记录排队等待时长（Muda 数据）。

**F4 定时任务（P1，G9）**——创建任务时可选"定时/重复"（每天/每周/工作日 + 时间点）。到点由 Runtime 自动发起（走同一 WIP 队列），产生的任务与手动任务无异。用例：每早 8 点跑"昨日 AI Agent 动态简报"。
验收：设定每日任务，连续两天自动产出交付物，通知送达。

**F5 预算与成本控制（P0，G5）**——三层：任务级预算（创建时可设，默认取设置页全局默认值）；达到 80% 软告警（任务页黄条 + 通知）；达到 100% 触发 Andon（停线，用户选择追加预算或取消）。模型调用前预检：本次调用预估成本若将击穿预算，先停线。
验收：给任务设 $0.10 预算，注入高消耗场景，任务在击穿前停线且已完成部分可恢复。

### 3.2 多 LLM 接入与模型路由

**F6 多 Provider 适配（P0，G4）**——Model Adapter 扩展为 provider 注册表：Anthropic（已有）、OpenAI 兼容端点（覆盖 OpenAI/DeepSeek/Moonshot 等一切兼容 API）、Google Gemini、本地 Ollama。每个 provider：baseUrl + key（safeStorage，沿用现有密钥通道）+ 模型列表。统一消息格式在 Adapter 层归一。
验收：设置页配置两个 provider，同一 Recipe 分别指定运行，均可交付；密钥全部走加密存储。

**F7 按步骤路由（P0）**——路由粒度是 **Step kind 而不是任务**：Recipe 的每个 model 步骤声明 tier（`planning` / `generation` / `extraction` / `review`），设置页维护一张 tier → 模型 的映射表（如 planning→claude-opus，generation→claude-sonnet，extraction→本地 Ollama）。**路由表是配置常量，不做策略 DSL**——守裁决第 4 条精神，等真实使用暴露不够用再升级。
验收：深度研究任务中，报告生成用强模型、来源标题清洗用快模型，成本对比单模型下降且质量验证仍通过。

**F8 模型故障转移（P1）**——provider 返回 429/5xx 且重试耗尽时，若 tier 映射表配了备选模型则自动切换并在账本记录 `model-fallback` 事件（Andon 之前多一道自愈）；无备选则照常 Andon。
验收：注入主模型持续 500，任务经 fallback 用备选模型交付，复盘卡显示切换记录。

### 3.3 工具与能力生态

**F9 MCP Client 接入（P0，G6）**——用官方 `@modelcontextprotocol/sdk`，MCP Server 作为 Runtime 的 child process 管理（启停/健康检查/崩溃重启）。每个 MCP tool 包装为 ToolDefinition（provider='mcp'）进统一 Registry：**默认 baseRisk=approval_required，用户可在设置页按工具降为 low 或升为 forbidden**——MCP 不允许黑箱执行的落点就在这里。设置页 MCP 区：添加 Server（命令 + 参数 + env）、工具清单与风险等级管理。
验收：接入一个真实 MCP Server（如文件系统或搜索类），其工具出现在 Registry，调用记录完整落 tool_calls，高风险调用走 Approval。

**F10 Shell 工具（P1）**——`shell.run`：默认 forbidden；用户在设置页显式开启后变为 approval_required（每次执行都要批准，展示完整命令 + cwd）；白名单命令前缀（如 `npm test`、`git status`）可降为 low。执行在独立子进程、超时强杀、输出截断落账本。这是代码类 Recipe（跑测试、构建验证）的前置能力。
验收：文件/代码 Recipe 增加"运行测试"步骤，命令经批准执行，退出码作为确定性验证输入。

**F11 文件能力扩展（P1）**——`fs.read` 支持 PDF（文本层提取）与 xlsx/csv（表格转结构化文本）；`fs.list` 目录清单（low 风险）；输入支持文件夹（批处理 Recipe 的前置）。图片输入走多模态模型通道（F6 完成后）。
验收：拖入一个 PDF 发起摘要任务端到端交付，引用核验用页码 locator。

**F12 Computer Use（P2）**——只做评估性 spike，不进 v1.0。

### 3.4 上下文与知识沉淀

**F13 Projects 落地（P1，G7）**——按裁决第 2 条保持人工容器：Projects 一级导航页；项目 = 名称 + 说明 + Saved Instructions（一段稳定偏好文本，创建任务时自动注入 prompt）+ 手动关联的文件/任务/交付物。创建任务时可选归属项目。**不做自动总结、不做上下文自动选择**——升级条件（单项目 20+ 任务且频繁上下文遗漏）触发后再议。
验收：建"某客户营销"项目，其下任务自动带上项目 Saved Instructions，项目页聚合展示其任务与交付物。

**F14 Recipe 生态演进（P1）**——分两步走，都不违反"不序列化可执行步骤"的裁决：
① 预设增强：预设支持参数占位（goal 模板中 `{{topic}}` 之类，发起时填空）；
② **Recipe 组合器**：步骤实现仍是代码内的 Step 库（read / search / fetch / generate / verify-citations / verify-rules / write / deliver…），用户在 Library 里用现成步骤**排列组合 + 配参数**（如换验证规则词表、改来源数量）生成自定义 Recipe，存库的是步骤 id 序列 + 参数 JSON，不是可执行代码。
验收：不写代码组合出"读取文件夹→逐个摘要→合并成周报→规则检查→交付"的自定义 Recipe 并跑通。

**F15 Kaizen 激活：Recipe 版本与 Eval Cases（P2）**——裁决约定"新 Recipe 实际需要某字段时再增加"：当自定义 Recipe 出现后，激活 LoopTemplate 的 version 与 evalCases 字段，改 Recipe 前用固定用例对比新旧版本。v1.0 只留数据位，不建 UI。

### 3.5 Evidence 与验证深化

**F16 来源快照持久化（P1，G10）**——web.fetch 除提取文本外，原始 HTML 落盘到 `<dataDir>/snapshots/<hash>.html`（Artifact 记 snapshot 路径）。Evidence 点击优先打开本地快照（原文改版/失效也能回到抓取时刻的现场）。快照目录支持按任务清理。
验收：交付的研究报告在断网状态下仍可逐条回看引用原文。

**F17 规则验证场景库（P1）**——按裁决第 3 条"按场景增加"：把 content-pack 的规则检查泛化为可配置规则集（禁用词表 / 长度 / 必含结构），存库、可在 Recipe 组合器中引用。仍是确定性验证，不是通用 Verification Engine。

**F18 Model Review 软验证（P2）**——升级条件（三条 Recipe 出现明确重复需求）目前未触发。挂起，v1.0 不做。

### 3.6 交付物体验

**F19 富预览（P0，G8）**——Deliverable 预览升级：Markdown 渲染（标题/表格/代码块/引用角标可点）、图片内联、CSV 表格化。渲染在 Renderer 沙箱内完成（禁远程资源加载，CSP 收紧同步做）。加导出按钮（复制 / 存为 PDF / 另存为）。
验收：研究报告在应用内以渲染态阅读，引用角标点击直达 Evidence；一键导出 PDF。

**F20 版本对比 UI（P1）**——同一 Deliverable 的版本链（F1 会高频产生 v2/v3）提供并排 diff 视图（复用现有 unifiedDiff）。

## 4. UI/UX 优化路线

在记录 G 动效规范基础上，四个方向：

**U1 信息架构补全（P0）**：侧边栏变为 Home / Tasks / Projects / Deliverables / Library / Settings + Advanced(Run Inspector)——与 Stage1 第 6 节的目标架构对齐。Home 瘦身回"输入 + 需要你处理 + 进行中 + 最近交付"，历史任务全部迁往 Tasks。

**U2 键盘优先（P0）**：⌘K 命令面板（发起任务 / 跳任务 / 切页面 / 搜索交付物，全部无动画——高频键盘动作原则）；⌥Space 菜单栏迷你面板升级为真实输入框（快速交代任务不唤起主窗）；任务页快捷键（⌘↩ 批准、Esc 返回）。

**U3 进度呈现升级（P1）**：Running 任务的当前步骤展示流式动作短语（现在只有步骤名）；Focus 摘要点击定位到 Run Inspector 对应 Step（Stage1 的"同一数据两种投影"承诺补完）；长任务的步骤列表加预计耗时参照（取该 Recipe 历史 Run 中位数——数据已在库里）。

**U4 视觉打磨（P1）**：应用图标与 Dock/Tray 成套视觉；空状态插画统一；退出动画基础设施（延迟卸载封装一个 `<Presence>` 小组件，卡片消失不再瞬移——记录 G 的已知遗留）；隔天慢速回放复审一轮全部动效。

## 5. 工程与质量基建

**E1 E2E 测试（P0，G13）**：Playwright 的 Electron 驱动跑真实应用：发起任务→批准→交付→预览 的主路径 + Andon/Blocked 两条异常路径，进回归基线（9 冒烟 + N 条 E2E）。这是后续所有 UI 迭代的安全网，排 M1 而不是最后。

**E2 DB 迁移框架（P0，G14）**：版本化 migration（`schema_version` 表 + 顺序迁移函数数组），把现有 origin/presets 迁移收编。v1.0 的每个新表（queue、schedules、projects、custom_recipes、rules）都会用到，必须先行。

**E3 性能与数据治理（P1）**：run_events 无限增长——归档任务的事件压缩为摘要行（保留统计，原始行移入 `run_events_archive` 或按保留期清理，用户可配）；任务列表虚拟滚动（100+ 任务）；快照目录配额。

**E4 打包与更新（P0，G15 / W4-B3）**：electron-builder 产 dmg + zip，Developer ID 签名 + notarize（等你的证书）；electron-updater 接自托管更新源（GitHub Releases 私有仓或本地静态目录）；崩溃日志本地留存 + 一键导出诊断包（日志 + 环境信息，**不含任务内容与密钥**）。

**E5 回归基线扩展（持续）**：每个 P0 功能落地时同步扩冒烟：队列场景（5 任务 3 并发）、预算击穿场景、增量 Run 场景、模型 fallback 场景。预计 v1.0 收口时基线为 15±2 个冒烟场景 + E2E 主路径。

## 6. 里程碑计划

四个里程碑，每个以"回归全绿 + 里程碑验收单"收口，延续 subagent 执行 + 独立审计的工作模式。排序逻辑：先把安全网和地基（E1/E2）打进 M1，再堆功能。

| 里程碑 | 周期 | 内容 | 验收门 |
|---|---|---|---|
| **M1 任务中枢** | 3 周 | F2 Tasks 页+看板、F3 WIP 调度、F5 预算控制、F1 增量 Run、U1 信息架构、E1 E2E 基建、E2 迁移框架 | 5 任务并发排队正常；预算停线冒烟通过；增量 Run 产出 v2 交付物；E2E 主路径进回归 |
| **M2 模型与工具** | 3 周 | F6 多 Provider、F7 按步骤路由、F8 故障转移、F9 MCP 接入、F10 Shell 工具 | 双 provider 交付；tier 路由成本对比达标；一个真实 MCP Server 全链路受控调用；fallback 冒烟通过 |
| **M3 知识与深化** | 3 周 | F13 Projects、F14 Recipe 组合器、F16 来源快照、F17 规则库、F4 定时任务、F19 富预览、F11 文件能力 | 自定义 Recipe 无代码跑通；断网回看引用；定时任务连续两日自动交付；PDF 输入端到端 |
| **M4 发布** | 2 周 | E4 打包签名+自动更新、U2 键盘优先、U3/U4 打磨、F20 版本对比、E3 数据治理、全量验收 + 实网回归 | 签名 dmg 可分发安装；自动更新走通一次；全部回归基线 + E2E 全绿；15 条 MVP 验收标准复检 |

总计约 **11 周**到 v1.0。M1 结束即可日常自用（多任务 + 增量修改），M2 结束具备成本优势，M3 结束功能完备，M4 可对外分发。

## 7. 裁决表对照：哪些冻结项在 v1.0 解冻

Stage1 第 14 节的六项裁决在本计划中的状态——**只有触发了当初约定的升级条件才解冻**：

| 裁决项 | v1.0 状态 | 依据 |
|---|---|---|
| Evidence 不确定性字段 | ❄️ 继续冻结 | 引用错误案例库尚未积累 |

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| F1 增量 Run 的"受影响步骤判定"是全计划最难的模型问题，判错会重跑过多或漏跑 | 第一版保守策略：固定从生成步骤检查点起跑（等价"带上下文的重生成"）；账本记录用户对增量结果的接受率，数据支撑后再做精细判定 |
| WIP 调度引入队列后，与 Approval/Andon 的挂起语义交织，状态机复杂度上升 | 排队只发生在 queued 状态之前（新增 queued_waiting 内部状态映射 Running），不触碰现有挂起路径；先写状态机单测再写调度器 |
| 多 provider 的消息格式差异腐蚀 Adapter 层 | 归一层只支持"单轮指令 + 文本输出"这一当前实际用法，不做通用聊天抽象 |
| MCP Server 质量参差，子进程失控 | 沿用 Andon：MCP 崩溃 = 工具调用失败 = 停线；健康检查失败自动降级禁用该 Server 并通知 |
| 组合器可能滑向工作流画布（违背产品定位） | 组合器只在 Library 里、只做线性步骤序列、不做条件分支；需要分支的场景写成新的内置 Recipe |
| 11 周计划的进度风险 | 每个里程碑内部 P0 先行；M3 的 F4/F11 是首选缓冲牺牲项；M1/M4 不可压缩 |
