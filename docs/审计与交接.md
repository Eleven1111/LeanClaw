**依赖审计**（截至 2026-07-25 核实；这类断言会随新公告腐烂，**不要只记数字，按下面的分层判据复核**）：

- **发布风险面用 `npm audit --omit=dev` 判定**——只有 prod 依赖会进 `.app`。当前 **2 moderate**：`@hono/node-server` 的 Windows `serve-static` 编码反斜杠路径穿越，经 `@modelcontextprotocol/sdk` 传入。本机 macOS-only 且 MCP 走 stdio 传输，不起该 HTTP 静态服务，判定不可达。
- **全量 `npm audit` 另含 16 项 dev 链 high**（electron-builder → `@electron/asar` / `glob` / `minimatch` / `ejs` / `temp` 等），不进 `.app`，风险面是构建机与构建产物完整性。
- **不采纳 `--force` 的理由要看 `fixAvailable` 的方向**：上述 18 项的 `fixAvailable` 全部指向**降级**（`electron-builder@25.1.8`、`@modelcontextprotocol/sdk@1.24.3`），不是上游修复。降级会退回一个公告尚未覆盖的旧版本，并放弃已实测通过的打包链。
- **复核方法**：`--omit=dev` 判发布风险；全量 `npm audit` 只用于发现 dev 链是否出现**非降级**的可修项（`fixAvailable: true`），出现即用 `npm audit fix` 白拿。2026-07-25 即以此修掉 `postcss` high 与 `tar` moderate（20 → 18 项），`package.json` 未动、无任何降级。

**架构不变量**（违反即审计不通过）：状态转换只经 `state.ts::transition()`；delivered 唯一入边是 verifying；工具调用必经 Registry + 三级风险；不可逆写入必过 Diff+Approval；事件只追加不修改；关键失败必须停线；步骤可重入、写入幂等；Renderer 保持 sandbox。

### 记录 AT：列表投影性能债清偿与性能闸门收紧（2026-07-25）

**归因先于修复**：记录 AR 把 8.4 秒记为「`listTaskViews()` 的逐 Task 投影 N+1，应改为批量查询」。实测推翻了这个诊断的重点。用真实 v12 库灌入等规模夹具（1000 Task / 20 万事件）并复刻 `buildTaskView` 的 13 条查询逐条计时后：**`run_events` 计数一项占 7405ms 中的 7370ms（99.5%）**，其余 12 条查询合计 13ms。补上真实的 Run/Step 数据后总量升至 15997ms，其中事件计数 11465ms、步骤时长参考 `historicalDurations` 查询 2348ms + 解析 2058ms。批量化投影是最大的改动却是最小的收益；真正的两个原因是：

1. **全库零索引**——`grep CREATE INDEX src/` 结果为空。`run_events` 20 万行上每个 Task 跑一次 `COUNT(*) WHERE task_id = ?`，1000 次全表扫描约 2 亿行访问。
2. **`historicalDurations` 是二次方的**——同一 `recipe_id` 的查询结果完全相同，却对每个 Task 重跑一次，每次返回全部历史 Step 再逐行 `new Date()` 解析两次。加索引救不了它，因为这不是选择性问题而是重复劳动。

**修复**：migration **v13** 建立 13 个热路径索引（`steps` 由既有 `UNIQUE(run_id, idx)` 覆盖，不重复建）；新增 `src/runtime/step-durations.ts`，`listTaskViews()` 用 `buildStepDurationIndex()` 一次查询构建全 recipe 的时长索引后传给 `buildTaskView`，单任务路径（`publishTask`）保留只查该 recipe 的回退入口，行为不变。基准实验：加索引 15997ms → 4096ms，再提取步骤时长 → **47ms**。

**闸门本身也是坏的，一并修正**：原 `expect(taskHydrationMs).toBeLessThan(60_000)` 对一个 8.4 秒的操作设 60 秒阈值，要劣化 7 倍才会红；夹具只造 9 个 Run、**0 个 Step**，990 个任务连 Run 都没有，`historicalDurations` 这条真实路径完全未被覆盖（这正是它此前没被发现的原因）。现夹具为每个 Task 建 Run 与 7 个 Step（21–29 保留原 run id 与 failed 状态以免影响验证失败断言），阈值收紧至 **8000ms**——取最坏观测值约 3 倍，既能对退回旧行为决定性报红，又不至于抖动。另在旅程 E 增加不依赖机器速度的**结构断言**：v13 全部 13 个索引存在，且 `EXPLAIN QUERY PLAN` 证明事件计数确实走 `idx_run_events_task` 而非全表扫描。
